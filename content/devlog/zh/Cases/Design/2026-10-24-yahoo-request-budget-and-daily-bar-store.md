# Yahoo 请求预算与日线库

KairoTrade 的服务端要向 Yahoo 拉 sparkline 和日线。从 10/24 到 10/30 的四次会话里，三项改动给服务端调用 Yahoo 的频率定了上限：

1. **日内请求合批。** 服务端为日内 sparkline 调用 Yahoo 的次数，从每天约 21,600 次（#80 初稿）降到每个工作日约 1,250 次。
2. **Redis 里的日线库。** 180 个标的，每个约 370 天，先一次性填满，之后每个工作日补一次。
3. **公共数据的 cache key 约定。** 格式是 `public:<kind>:v<n>:<id>` ，所有用户请求相同的公共数据时，读的都是同一个共享条目。

==预算来自两件事：每次上游调用都挪进定时任务，页面只读服务端已经有的数据。== 最后一步在 10/30，研究页的报价也改成从存储读取（#204）。

过程中逐个核对了第三方数据源的条款。StockTwits 只拿来参考渲染方式，没取它的任何数据。

## 背景与约束

- sparkline 是列表里标的旁边那条小价格线。这里用 Yahoo 的 spark 接口画，取一天里 15 分钟或 5 分钟的收盘价。
- 请求太多时，Yahoo 返回 HTTP 429（Too Many Requests）。这是它的 rate limit（限流），也就是单位时间内的请求上限。下面的调度器和回填遇到 429 都会退避。
- 期货 `MES` 和 `MNQ` 的实时数据不经过 Yahoo，来自 TradingView feed，走 SSE（server-sent events，单向的 HTTP 更新流），退避策略是 `LIVE_BACKOFF` 。
- 有些候选数据源在条款里禁止自动访问。还没谈到数据量，这条限制就先划定了哪些数据能拿。

源材料记录的是改动前后的状态，没有事先写好的方案清单。下面按时间顺序讲，附上每一步给出的数字。

## 10/24：日内请求预算

发布 [[zh/Glossary/PR|PR]] #85（`integration/ticker-1` → main，`1965311` ）带了六个 PR，其中三个定下了预算：

| PR | 改动 |
| --- | --- |
| #80 | 调度器给每个数据源设周期；spark `1d`/`15m` ；每批 20 个标的；每个时段最多 3 次 Yahoo 请求；遇到 429 停掉当前时段；日内数据源排在队列前面 |
| #84 | 非交易时段 15 分钟一档的时段里，限流标记保留整个时段 |
| #81 | 浏览器的自选列表、滚动行情条和行情表共用 `useIntradaySparks` 这一个 store，每 150 s 发一次批量请求 |

数字：

| 路径 | 之前 | 之后 |
| --- | --- | --- |
| 服务端 → Yahoo | #80 初稿：每个时段每个标的 1 次请求，52 个标的，≈ 21,600 次/天 | 每个时段最多 3 次请求，工作日 ≈ 1,250 次/天 |
| 浏览器 → 服务端 | 自选列表、滚动行情条和行情表各自请求 | 每 150 s 一次批量 `/api/spark` ；不再轮询报价快照 |
| 期货 | — | `MES`/`MNQ` 走 TradingView SSE，退避 `LIVE_BACKOFF` |

时段安排能解释这两个数字。美东时间 04:00 到 20:00（含盘前盘后）每 2.5 分钟一个时段，其余时间每 15 分钟一个，一天共 384 + 32 = 416 个时段。下面这笔账是按时段安排推出来的，不是从源材料里抄的：

```
before:  52 symbols × 1 request  × 416 slots ≈ 21,600 requests/day
after:   ⌈52 / 20⌉ = 3 batches   × 416 slots ≈  1,250 requests/day
```

2.5 分钟这个周期和对 StockTwits 做的只读探测结果一致。探测测的是它的 sparkline 怎么刷新，结果是它的批量接口缓存约 2.5 分钟。本站照搬的是渲染方式（`svg` 里放 `polyline` ，`viewBox 0 0 W 32` ，描边 1.33）和这个刷新频率，没有搬数据。

### 数据源条款

同一次会话读了所有在用或在考虑的第三方数据源的条款：

| 数据源 | 条款 | 结果 |
| --- | --- | --- |
| StockTwits | §5 禁止未经书面许可或未经批准 API 的自动抓取；API 文档页返回 404 | 没取数据；只参考渲染 |
| Quiver | §8 禁止机器人访问；§6 规定 Quiver Data 只限个人、非商业使用，不得再分发；商用需要付费档 | 现有的披露数据抓取和这条冲突；交给负责人决定 |
| Rallies | 页面由 JS 渲染；#30 记录过 robots.txt 禁止 `/api/` ，条款禁止爬取 | 只允许用带 key 的官方 API |
| ai4trade | 所有路径都返回同一个 [[zh/Glossary/SPA\|SPA]] 外壳；没有条款 | 没有授权，不启用 |

10/29，#143 移除了 Rallies 数据源和它的模型排名。

## 10/25：spark 修复和日线库

三个 sparkline 路径的修复直接进了 main：

| PR | 改动 |
| --- | --- |
| #87 | 去掉 `includePrePost` ，Yahoo 的 spark 接口遇到它返回 400，`1d` 快照已经空了 13 小时 |
| #90 | 默认日内列表是 22 个标的（6 个指数 ETF、11 个行业 ETF、4 个期货、NVDA），每个时段 2 次请求 |
| #95 | 5 分钟 bar，一天 78 个点；sparkline 按 64×24 真实像素绘制，线宽 1.25，不拉伸 |

22 个标的按每批 20 个分，是两批，所以每个时段两次请求。

日线库（issue #92，PR #94，在发布 PR #97 里上线）取代了每 12 小时重新拉两年历史的做法：

| 项目 | 值 |
| --- | --- |
| 标的 | 180 个：`companyLogos.ts` 里的 161 个加首页的 22 个，去重后 |
| 存储 | Redis，列式数组，每个标的约 370 天 |
| [[zh/Glossary/TTL\|TTL]] | 400 天 |
| 大小 | 每个标的约 12 KB，总共 2-3 MB |
| 回填 | `range=1y` ，请求间隔 2 s，分摊到每分钟的 tick 上；遇到 429 暂停 15 分钟 |
| 每日更新 | 工作日美东 20:30，`range=5d` ，按日期合并 |
| 部署后检查 | 10 分钟后：AAPL 和 MSFT 各 250 根 bar，最后一根是 2026-10-23 |

TTL（time to live）是条目存进 Redis 后能活多久，到期 Redis 就删掉它。

日线每天的 Yahoo 请求数：

| 方案 | 请求数 |
| --- | --- |
| 旧：每 12 小时，每个标的，两年历史 | ≈ 60/天 |
| 新：回填 | 180，一次性 |
| 新：之后 | 每个工作日 180，另加每个日内时段 2 次 |

新方案每天的日线请求比旧方案多，但覆盖了 180 个标的，而且每次请求只拉 5 天，不是两年。

## 10/29：K 线存储

#139 加了 K 线存储（Codex 做了两轮，评审提的九个黄色项全部修复）。K 线就是蜡烛图上的一根 bar：开盘、最高、最低、收盘（OHLC）。

| 项目 | 值 |
| --- | --- |
| 期货 | `MES1!` 、`MNQ1!` 、`MGC1!` 、`MCL1!` ；5m、15m、1h 和 1d；每个 600 根 |
| 日线 | 235 个标的加各个自选列表 |
| key 前缀 | `ohlcv:v1:` |
| 序列上限 | 48 |
| 活跃集合 | 约 6.5 MB，低于 Redis 的 128 MB 上限 |

存储的数据来自 TradingView sidecar 的 `/history` 接口。这个调用失败时，日线序列回退到 Yahoo。上线当天 sidecar 的 `/history` 正在失败，存储一直是空的；那次故障见 [[zh/Cases/Debug/2026-10-26-tradingview-intraday-snapshots-stuck-pending|2026-10-26-tradingview-intraday-snapshots-stuck-pending]]。

#153 跟进了几处：

- 每个静默返回现在都会记录 `reason` ；
- 空结果不再做 1 小时的负缓存（负缓存把“没有数据”也存起来，下一个调用方就不用再问）；
- 拉取失败会在 5 分钟内重试；
- sidecar 请求超时从 12 s 改为 20 s。

## 10/30：公共数据缓存

issue #196 把共享的行情数据统一到一套 key 约定下：

```
public:<kind>:v<n>:<id>
```

这个 key 由所有用户共享，私有 key 则带上用户的哈希。

cache key 是条目存储时用的名字。两个请求拼出相同的 key，读的就是同一个条目。版本段 `v<n>` 让格式变更时直接写新条目，不会误读旧条目。

| PR | 改动 | 评审后的修改 |
| --- | --- | --- |
| #201 | 日内信号分块共享；key 保留 7 天 | 上下文锚定到交易时段（306 根 bar 加当天）；提前收盘只计一次 |
| #202 | 长日线快照保留 7 天，合并最新数据 | 刷新后的快照可以修正历史；只有 404 做负缓存 |
| #203 | `data-sources` 缓存 60 s；registry 去重；宏观数据只发缺的条目 | 驱逐掉的注册可以恢复；无效判定 1 小时后重试 |
| #204 | 研究页报价从存储读；Finnhub 认证失败的退避从 1 小时延到 24 小时 | 过期的日内快照标记为 stale；12 行的自选列表遇到 429 只调 1 次，不再是 36 次 |
| #207 | key 辅助函数和静态测试 | 测试拒绝空 key、手写的私有 key，以及按任意字段名做缓存 |
| #208 | Redis 统计和 prompt 哈希日志 | 无 |

交叉评审：Codex 评审了 #202 和 #203；claude2 评审了 #201、#204 和 #207。

随之定下两条规则：

- **公共路径读存储，未命中也不去调上游。**
- **私有数据绝不放在公共 key 下。** 审计没有发现这种情况，日志里既没有 prompt 文本，也没有用户 id。

实际命中率没有测。

## 候选方案

源材料记录的前后对照：

| 问题 | 之前 | 之后 | 决定因素 |
| --- | --- | --- | --- |
| 服务端怎么向 Yahoo 要 sparkline | 每个时段每个标的一次请求 | 每批 20 个，每个时段最多 3 次 | ≈ 21,600 vs ≈ 1,250 次/天 |
| 浏览器怎么拿 sparkline | 每个组件各自请求 | 共用一个 store，每 150 s 一次批量请求 | 每 150 s 一次批量请求就够三个组件用 |
| 日线历史从哪来 | 每个标的每 12 小时重拉两年 | Redis 日线库，回填一次，每个工作日 `range=5d` | 覆盖 180 个标的；每次更新只拉 5 天 |
| 取哪些第三方数据 | — | 只取条款允许的数据源 | StockTwits、Quiver、Rallies 和 ai4trade 的条款 |
| 共享数据怎么缓存 | — | `public:<kind>:v<n>:<id>` ，用静态测试检查 | 每条公共数据一个条目；共享 key 里没有私有数据 |

## 决定

Yahoo 流量的上限由时段安排和批大小决定，跟有多少人在看无关。页面访问读的是共享的 sparkline 批次、Redis 日线库或某个 `public:` key。调用 Yahoo 的只有调度器、日线任务和回填，这三处遇到 429 都会退避。

## 模块划分

| 单元 | 职责 |
| --- | --- |
| 时段调度器（#80、#84） | 每个数据源一个周期；每批 20 个；每个时段最多 3 次请求；遇到 429 停止 |
| `useIntradaySparks`（#81） | 浏览器端共享 store；每 150 s 一次批量 `/api/spark` |
| 日线库（#94） | Redis 里 180 个标的；从 Yahoo 回填和工作日更新 |
| K 线存储（#139、#153） | `ohlcv:v1:` 下的期货和日线 OHLC；数据来自 sidecar 的 `/history` |
| key 辅助函数和静态测试（#207） | 生成 `public:` 和私有 key；拒绝手写的 key |

## 数据流

1. 调度器在自己的时段醒来，把标的列表按 20 个一批分组，最多发 3 次 Yahoo 请求。
2. 服务端保存最新一批数据。
3. 每个打开的页面每 150 s 发一次 `/api/spark` 请求，读这批数据。
4. 日线来自 Redis 日线库，日线任务在工作日美东 20:30 更新它。
5. sparkline 以外的共享数据放在 `public:` key 下，未命中不调上游。

## 范围之外（YAGNI）

- 50 个条目的 spark registry 在各个 range 之间共享。只有首页把它挤满时，`1d` 才单独开一张表。
- 2.5 分钟的时段窗口没有缩到美东 09:30-16:00。
- 日线库没有加入完整的 S&P 500。
- 报价接口没有成交量和当日高低价，所以首页表格只有五列。
- 要不要预热长日线快照（约 400 × 130 KB）还没定。
- 公共响应的缓存头和轮询频率（#196 的 F7）还没做。
- 主机上 Redis 的持久化和驱逐策略还没确认，检查命令是 `redis-cli CONFIG GET save` 。

参见 [[zh/Techniques/yagni-and-designing-for-present-requirements|yagni-and-designing-for-present-requirements]]。

## 经验与小技巧

- 用算式写出请求预算：标的数、批大小、每天的时段数。#80 初稿一乘出来，21,600 这个数就摆在眼前。
- 让调度器负责所有上游调用，页面只读它存下的数据。这样上游流量取决于时段安排，和看的人数无关。
- 写抓取脚本之前先读数据源的条款。这里四个数据源有三个在条款里禁止自动访问。
- 负缓存的触发条件要窄。#202 只缓存 404，#153 不再缓存空结果，因为空答案可能只表示上游挂了。
- 每个 cache key 都带上版本 `v<n>` ，格式变更时写新条目，不会误读旧条目。

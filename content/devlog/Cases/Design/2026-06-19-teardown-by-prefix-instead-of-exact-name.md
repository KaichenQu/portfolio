# Teardown: deleting by prefix instead of by exact name

The CS6620 teardown script cleans up the AWS resources this assignment creates: Lambda functions, IAM roles, layers, and a REST API. It originally deleted them one at a time, by the full names hardcoded in `config.py`.

## Background and constraints

The trigger was a failed run. Teardown reported `Role not found: cs6620-a2-size-tracking-role`, yet the function itself deleted fine. Checking the real account:

```bash
aws iam list-roles --profile admin --query "Roles[].RoleName" --output text
```

The actual role name is `cs6620-a2-size-tracking-role-l9kbz5d9` — ==AWS appended a random suffix to the role, so a teardown that hardcodes the full name can never match it.==

Constraints:

- Cleanup must still work after a rename ("whatever I name it, it gets deleted").
- Never touch AWS's own service-linked roles (the five `AWSServiceRoleFor*`).
- Keep the existing structure: still read `config.py`, still use the same boto3 session.

## Candidate options

### Option A: keep exact names, but list and fuzzy-match before teardown

- Approach: list every role in the account, delete anything whose name contains the assignment name.
- Upside: small change.
- Cost: "contains" matching is far too wide and easy to over-delete; the logic ends up scattered.

### Option B: prefix matching (chosen)

- Approach: define `RESOURCE_PREFIX = 'cs6620-a2'` and delete every function, role, layer, and API whose name starts with it, whatever random suffix AWS tacked on.
- Upside: immune to random suffixes; as long as every resource is created with that prefix, deploy and teardown line up by construction; the decision lives in one place.
- Cost: too short a prefix can catch unrelated resources, so it needs an allowlist protecting the default resources.

## Decision

**Option B.** The root cause is AWS's random suffix, and prefix matching addresses exactly that; and "delete cleanly under any name I choose" is, at bottom, a request to relax matching down to the prefix.

Two safety boundaries:

1. Only delete resources starting with the given prefix. `str.startswith` accepts a tuple, so when assignment1's leftovers (prefix `size-tracking-lambda-`) later needed cleaning too, adding one more prefix to the tuple was enough — no logic change.
2. Always skip service-linked roles, the ones whose path is `/aws-service-role/`, so AWS's built-in roles are never touched.

## Module split

- `config.py`: the single source of names, with `RESOURCE_PREFIX` added. Deploy and teardown both read only from here, so a rename is a one-place edit.
- `teardown_lambdas.py`: enumerates and deletes the four resource kinds by prefix. Deleting a role first detaches its attached policies and removes its inline policies, since AWS refuses the delete otherwise. Enumeration goes through a paginator so nothing past the first page is missed.

## Data flow

`config.RESOURCE_PREFIX` → teardown lists each resource kind with a paginator → the name `startswith(prefix)` and is not service-linked → delete.

## Not done (YAGNI)

No configurable "matching rule engine", no regexes. A prefix plus one service-linked allowlist covers the requirement, and extra abstraction would only cost reading effort.

## Lessons and tricks

- **When names are generated by the platform and may carry a random suffix, match on the stable prefix, not the full name.**
- **Bulk deletion needs one hard boundary stating what must never be deleted** (here, service-linked roles), and that boundary should be explicit and readable rather than relying on the prefix happening not to match.
- **Give deploy and teardown one shared source of names** (`config.py`), which kills "what got created and what gets deleted don't line up" at the source. This is what [[drawing-module-boundaries]] calls grouping by reason to change.
- Enumerate cloud resources with the SDK's paginator; never assume one page holds everything.
